## 操作序列（可复现）
1. API 政策巡检：`instabox_api.py ls`（5 台状态与规格）、
   `usage`（限额与存储）、`snapshots`（快照清单）。

uptime 冻结核查（第七次复现，test-1 第六时段）：
- 上轮（E-20261026-001）00:17:06 实测：uptime -s
  2026-10-25 12:38:22 UTC，/proc/uptime 13123.93 秒（3:37:04）。
- 本轮 02:16:10 实测：uptime -s 2026-10-25 14:37:03 UTC，
  /proc/uptime 13146.78 秒（3:39:07）。
- 墙钟经过 16:17:06 → 18:16:10 = 1 小时 59 分 04 秒。
  uptime -s 前移 1 小时 58 分 41 秒。
- 两次读数之间 test-1 的状态：00:17:15 暂停（E-20261026-001
  轮末）→ 本轮 02:15:59 恢复，中间无其他恢复，单段暂停
  约 1 小时 58 分 44 秒，与前移 1:58:41 相差 3 秒，在暂停
  时刻取整误差内。
- uptime 增长 13146.78 − 13123.93 = 22.85 秒，与两次读数
  之间的运行总时长（暂停前约 9 秒 + 恢复后约 11 秒 ≈ 20 秒）
  相差约 3 秒，在读数时刻取整误差内。
- 校验和：前移 1:58:41 + 增长 0:00:23 = 1:59:04 = 墙钟经过，
  精确吻合，冻结模型自洽。
- 若是重启：恢复后 uptime 应约为恢复后经过的 11 秒，
  uptime -s 应约为 18:16 UTC；实测 3:39:07 与 14:37:03
  均不符，重启假设被证伪。
- 结论：本次恢复仍是冻结续跑，非重启；uptime 冻结在
  test-1 上第六时段复现（全部观测中的第七次），且本次为
  单段干净暂停，对照精度最高。

## 异常与边界
- InstaBox API 短暂 502（18:16:23 UTC，约 02:16:23 CST）：
  暂停 test-1 的首次尝试在 `resolve` 阶段（GET /v1/machines）
  即报 `HTTP 502 GET /v1/machines`（nginx 502 Bad Gateway 页），
  暂停操作本身未发出；随后同命令的 `ls` 复核也报同一 502。
  按连接器处置：等待 60 秒后重试一次，18:17:31 暂停成功
  （0.07 秒），API 自行恢复。特征与 2026-10-25 约 16:24
  的 API 502 事件一致（短暂闪断、约 60 秒自愈），未造成
  机器状态异常（test-1 在重试前仍为 running，暂停后正常
  回到 suspended）。已记入 incidents.md。非限流（无 429、
  无速率限制文案），未重试冲击。
- 本轮恢复延迟为 API 路径实测值，与前两轮控制台点击
  的分钟精度上界不可直接拼成同一分布；跨轮比较以
  "≤60 秒上界"与"秒级实测 2.05 / 2.59 / 4.67 秒"分别表述。

## 结论与调度建议
- 结论：02:15 深夜单机恢复创建→Running 4.67 秒
  （API 路径秒级实测），创建→操作成功 8.86 秒；与
  00:15 的 2.59 秒、20:15 的 2.05 秒同为个位数秒，深夜

  14:15、20:15、00:15、02:15），结论置信度仍低（均为
  单样本、两种计时路径）。
- 结论：uptime 冻结在 test-1 上第六时段复现（全部观测
  第七次）：uptime -s 前移 1:58:41 ≈ 单段暂停时长
  1:58:44，前移量 + uptime 增长量 = 墙钟经过精确吻合，
  冻结模型自洽。
- 结论：InstaBox API 偶发短暂 502（约 60 秒自愈），本轮
  与 2026-10-25 约 16:24 事件为第二次观测；恢复/暂停
  操作应按"先读状态再重试一次"的处置执行，502 本身不
  代表机器状态异常。
